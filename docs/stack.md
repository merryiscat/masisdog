# masisdog 스택 · 하네스

> 킥오프 인터뷰 3부 산출물. 흐름은 **케이스 → 스택 → 하네스** 한 방향.
> 2부 [usecases.md](usecases.md)의 케이스별 "필요 기술"을 케이스 밖으로 꺼내 중복을 걷어낸 결과다.
> `단계`: **1** = PC 원격 검증(현재), **2** = 온디바이스 앱 이식.

## 1. 기술 요구 집계 (4계층)

16개 케이스 + 공통 전제 A~D의 필요 기술을 합치면 4계층으로 수렴한다.

### ① 두뇌 계층 — 온디바이스 지능 (M0 벤치가 좌우)

| 스택 항목 | 쓰는 케이스 | 단계 |
|---|---|---|
| 온디바이스 LLM (판단·대화·역질문·사실추출·분류·초안) | 사실상 전부 | 1→2 |
| 온디바이스 비전 (화면·이미지 이해) = 공통 C | UC-4,5 · UC-1,2 폴백 | 1→2 |
| 온디바이스 STT + wake word = 공통 E(승격) | UC-5,14 | 2 |
| LLM 위키 저장·질의 (RAG 아님) = 공통 F(승격) | UC-13 · 여러 케이스가 사실 축적 | 1→2 |

### ② 폰 제어 계층 — 안드로이드 능력

| 스택 항목 | 쓰는 케이스 | 단계 |
|---|---|---|
| UI 조작·화면 읽기 (uiautomator2/mobile → Accessibility) | UC-1,2,4,5,7 | 1→2 |
| 관찰·학습 (UsageStats+위치+시간, 루틴 마이닝) = 공통 A | UC-1,2,6,7 | 1→2 |
| 알림·SMS 파이프라인 (파싱 + RemoteInput) = 공통 D | UC-3,7,8 | 2 |
| 트리거·센서 (geofence·activity·블루투스·IMU·충전) | UC-1,2,3,6,15 | 2 |
| 시스템 권한 능력 (통화거절=Shizuku, MANAGE_EXTERNAL_STORAGE, 휴지통 API, VPNService) + 권한 부활 체인 | UC-3,4,12 | 2 |
| 안전장치 (확인 게이트/사후 통지/정책) = 공통 B | UC-1,3,4 | 1→2 |

### ③ 외부 연동 계층

| 스택 항목 | 쓰는 케이스 | 선결 과제 |
|---|---|---|
| 공공 교통 실시간 API (+키) | UC-2,9 | 키 확보 여부 확인 |

### ④ 개발 하네스 계층 (1단계 검증 도구)

uv/Python · uiautomator2 · adb · mobile-mcp — **3부에서 고르는 대상은 여기뿐.** ①②③는 우리가 만들 런타임 능력이지 개발 도구가 아니다.

> **설치 범위(확정)**: 1단계는 **adb(platform-tools) 단독**이면 충분 — mobile-mcp·uiautomator2 둘 다 adb만 요구. **Android Studio는 불필요.** Android Studio는 2단계(온디바이스 네이티브 앱 빌드) 진입 시에만 설치. (에뮬레이터로 갈 경우엔 1단계에도 필요하나, 계획은 실물 폰.)

## 2. 스택 확정 (1부 가설 보정)

1부 가설 `mobile-mcp / uiautomator2 / adb + 온디바이스 LLM`에 집계로 **추가**된 것:

- 온디바이스 STT + wake word (음성이 UC-5·14의 본체 — 별도 트랙)
- 알림·SMS 파싱 파이프라인 (돈 케이스 3개의 토대)
- 센서·트리거 다양성 (케이스마다 다른 트리거)
- VPNService 트래픽 계층 (UC-12, plan.md 고유 강점)
- 공공 교통 API (유일한 실외부 연동 + 키)
- LLM 위키 저장 계층 (RAG 대신 확정)

**뺀 것**: 없음. 클라우드 비전만 "폴백 한정"으로 강등.

## 3. 하네스 판정

PLAYBOOK 프로필상 1단계는 **"Python 자동화 → 스킬 추가 없음, 글로벌로 충분"**. 하네스는 얇다.

| 하네스 | 스택 근거 | 판정 |
|---|---|---|
| `mobile` MCP | ② UI 조작 검증 (1단계 핵심) | 유지 |
| `context7` | ①② Android SDK·uiautomator2·llama.cpp 최신 문서 | 유지 |
| `github` | 저장소 운영 | 유지 |
| `sequential-thinking` | 관찰·학습/상태머신 로직 설계 | 유지(약) |
| `fetch` | ③ 교통 API 포털·문서 조회 | 유지(약) |
| `playwright` | 브라우저 자동화 — 스택에 웹 브라우저 없음 | **제거됨(2026-08-15)** |

**스킬**: 1단계엔 신규 불필요. 2단계(온디바이스 네이티브) 진입 시 검색할 후보 — 기기 연결 + 사용자 동의 후에만:
- `4ier/a11y-bridge` — Accessibility HTTP 브리지 (② 2단계 M3 자체 구현 참고)
- `4ier/agent-skills@termux-api` — Termux 폰 능력 접근 (온디바이스 LLM 호스팅)

## 4. 빌드 순서 — 15개 케이스 → 척추 + 트랙

MVP가 크므로 3부에서 우선순위로 정렬한다(발굴 땐 안 자름).

- **M0 (게이트)**: 온디바이스 LLM·비전·STT 성능 벤치 → 하이브리드 여부 결정. **모든 것의 선행.**
- **척추 1 — 읽기 전용 검증** (자율행동 X, 리스크 낮음): 관찰·학습(A) + 파싱(D) 파이프라인을 **UC-6 수면 · UC-8 지출 · UC-7 구독 · UC-16 문자 브리핑**으로 굳힌다.
- **척추 2 — 자율행동**: UI 조작 + 안전장치(B) → **UC-1 아침루틴**(플래그십) → UC-4·5.
- **별도 트랙** (각자 독립 스택): 음성(UC-5·14) / 네트워크 VPN(UC-12) / 센서 안전(UC-15) / 교통(UC-2·9).
